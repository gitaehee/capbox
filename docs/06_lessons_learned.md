# 06. 프로세스 적용의 교훈

## 1. 개요

본 문서는 CapBox 프로젝트를 진행하며 요구사항 분석, 설계, 구현, 테스트, 품질 관리에 이르는 소프트웨어 개발 프로세스를 적용한 결과와 그 과정에서 얻은 교훈을 정리한 문서이다.

CapBox는 스크린샷 이미지에서 텍스트를 추출하고, 추출된 텍스트를 저장한 뒤 나중에 검색어로 다시 찾을 수 있도록 돕는 웹 기반 아카이빙 서비스이다.

본 프로젝트에서는 바이브코딩을 활용하여 기능 구현 속도를 높였지만, 동시에 소프트웨어공학 프로세스를 함께 적용하여 요구사항의 범위 조정, 설계, 테스트, 품질 개선 과정을 체계적으로 기록하였다.

---

## 2. 프로젝트 진행 흐름

본 프로젝트는 다음 순서로 진행하였다.

| 단계 | 수행 내용 |
|---|---|
| 주제 선정 | 스크린샷 텍스트 아카이빙 서비스 아이디어 선정 |
| 요구사항 분석 | MVP 범위 확정, 기능/비기능 요구사항 작성 |
| 설계 | 화면 흐름, 데이터 구조, 모듈 구조 설계 |
| 구현 | Streamlit UI, OCR, SQLite 저장, 검색 기능 구현 |
| 중간 점검 | 요구사항 대비 구현 상태 확인 |
| 테스트 | OCR, 저장, 검색, 예외 상황 테스트 |
| 품질 관리 | OCR 한계, 검색 품질, 예외 처리 정리 |
| 회고 | 바이브코딩의 효과와 한계, 프로세스 적용 교훈 정리 |

이 흐름을 통해 단순히 결과물을 만드는 것이 아니라, 개발 과정 전체를 문서와 커밋으로 남기며 진행하였다.

---

## 3. 요구사항 분석 단계의 교훈

초기 아이디어는 사용자가 스크린샷을 찍은 뒤 모바일 앱으로 바로 공유하면, 앱이 이미지 속 텍스트를 추출하고 저장하는 방식이었다.

그러나 요구사항 분석 과정에서 다음 기능들은 과제 기간 안에 구현하기에 범위가 크다고 판단하였다.

- 모바일 앱 공유 기능
- 갤러리 자동 접근
- 사용자 계정 및 로그인
- 클라우드 저장
- 이미지 원본 저장 및 관리

따라서 이번 프로젝트에서는 핵심 가치를 다음과 같이 축소하였다.

> 스크린샷 이미지에서 텍스트를 추출하고, 나중에 검색 가능하게 저장하는 것

이 과정을 통해 얻은 교훈은 다음과 같다.

1. 좋은 아이디어라도 모든 기능을 한 번에 구현할 수는 없다.
2. 요구사항 분석 단계에서는 핵심 기능과 확장 기능을 구분해야 한다.
3. 바이브코딩을 사용할 때도 AI가 제안하거나 떠올린 기능을 모두 구현하기보다, 구현 가능성과 과제 목적을 기준으로 범위를 조정해야 한다.
4. MVP 범위를 명확히 정하면 이후 설계와 구현 방향이 안정된다.

---

## 4. 설계 단계의 교훈

설계 단계에서는 화면 흐름, 데이터 구조, 모듈 구조를 먼저 정리하였다.

CapBox는 다음과 같은 구조로 설계하였다.

- `app.py`: Streamlit 화면 및 사용자 흐름 제어
- `ocr_utils.py`: OCR 텍스트 추출
- `db.py`: SQLite 저장 및 조회
- `search_utils.py`: 키워드 검색, 유사도 검색, 하이브리드 검색

처음부터 모든 코드를 `app.py` 하나에 작성할 수도 있었지만, 기능별로 분리하여 설계하였다. 그 결과 OCR, DB, 검색 기능을 각각 독립적으로 수정하고 개선할 수 있었다.

설계 단계에서 얻은 교훈은 다음과 같다.

1. 구현 전에 화면 흐름과 모듈 구조를 정하면 개발 과정이 덜 혼란스럽다.
2. 기능별 책임을 분리하면 유지보수와 테스트가 쉬워진다.
3. 바이브코딩으로 생성된 코드도 프로젝트 구조에 맞게 배치해야 한다.
4. 설계 문서는 이후 구현과 품질 관리의 기준이 된다.

---

## 5. 구현 단계의 교훈

구현 단계에서는 바이브코딩의 효과를 가장 직접적으로 확인할 수 있었다.

AI를 활용하여 다음 기능의 코드 초안을 빠르게 작성할 수 있었다.

- Streamlit 기본 화면
- 이미지 업로드 및 미리보기
- EasyOCR 기반 텍스트 추출
- SQLite 저장 및 조회
- 키워드 검색
- 유사도 검색
- 하이브리드 검색

특히 새로운 라이브러리를 사용할 때, 기본 코드 구조와 함수 예시를 빠르게 얻을 수 있어 구현 속도가 빨라졌다.

하지만 구현 단계에서 다음 한계도 확인하였다.

1. AI가 만든 코드가 항상 현재 프로젝트 구조에 맞는 것은 아니다.
2. import 누락, 함수 연결 오류, 예외 처리 부족이 발생할 수 있다.
3. 기능은 동작해도 사용자 경험이나 품질이 충분하지 않을 수 있다.
4. 생성된 코드를 이해하지 않고 그대로 붙이면 이후 수정이 어려워질 수 있다.

따라서 바이브코딩은 구현 속도를 높이는 데 효과적이지만, 개발자가 코드의 역할과 흐름을 이해하고 검토해야 한다는 교훈을 얻었다.

---

## 6. 테스트 단계의 교훈

테스트 단계에서는 기능이 단순히 실행되는 것과 실제로 요구사항을 만족하는 것이 다르다는 점을 확인하였다.

예를 들어 OCR 기능은 정상적으로 동작했지만, 실제 테스트에서는 다음과 같은 오인식이 발생하였다.

| 원본 | OCR 결과 |
|---|---|
| 젤 | 절 |
| 살몬 | 살문 |
| 댓글 | 대글 |

이 결과를 통해 OCR 기능은 완벽하지 않으며, 사용자가 저장 전에 결과를 확인하고 수정할 수 있어야 한다는 점을 확인하였다.

또한 유사도 검색에서도 문제가 발견되었다.  
“아디다스 컨트리”를 검색했을 때 “자라 옷”, “인스타 릴스에서 본 옷”처럼 관련성이 낮은 결과가 함께 반환되었다.

이를 통해 얻은 교훈은 다음과 같다.

1. 기능 구현 후에는 실제 데이터로 반드시 테스트해야 한다.
2. OCR, 유사도 검색처럼 입력에 따라 결과가 달라지는 기능은 품질 편차가 크다.
3. 테스트는 성공 여부뿐 아니라 부분 성공과 한계를 기록해야 한다.
4. AI가 생성한 기능도 실제 사용 시나리오에서 검증해야 한다.

---

## 7. 품질 관리 단계의 교훈

품질 관리 단계에서는 테스트에서 발견한 문제를 바탕으로 보완 방안을 정리하였다.

적용한 품질 관리 방법은 다음과 같다.

| 품질 이슈 | 보완 방법 |
|---|---|
| OCR 오인식 | OCR 결과 수정 기능 제공 |
| 빈 본문 저장 | 저장 방지 및 경고 메시지 |
| 빈 검색어 입력 | 검색어 입력 안내 메시지 |
| 검색 결과 없음 | 결과 없음 안내 메시지 |
| 유사도 검색 부정확 | threshold 조정 및 하이브리드 검색 적용 |
| 모델 반복 로딩 | Streamlit cache 사용 |
| 개인정보 가능성 | 이미지 원본 미저장, 로컬 DB 저장 |

특히 유사도 검색의 한계를 보완하기 위해 하이브리드 검색 방식을 적용하였다.  
하이브리드 검색은 먼저 키워드 검색을 수행하고, 결과가 없을 때 유사도 검색을 수행하는 방식이다.

이 과정에서 얻은 교훈은 다음과 같다.

1. 품질 관리는 기능 완성 이후에만 하는 것이 아니라, 구현과 테스트 과정에서 계속 이루어져야 한다.
2. 바이브코딩으로 만든 기능도 품질 기준에 맞게 조정해야 한다.
3. 검색 기능은 하나의 방식만으로 충분하지 않을 수 있다.
4. 사용자에게 결과의 한계를 보여주고 수정 가능성을 제공하는 것도 품질 관리의 일부이다.

## 8. 바이브코딩의 효과

이번 프로젝트에서 확인한 바이브코딩의 효과는 다음과 같다.

### 8.1 개발 속도 향상

AI를 활용하여 기본 코드 구조, 함수 작성, 예외 처리 예시를 빠르게 얻을 수 있었다.  
특히 Streamlit UI, SQLite 연동, OCR 함수, 검색 함수 구현에서 개발 시간이 단축되었다.

### 8.2 아이디어 구체화

초기 아이디어였던 “스크린샷을 앱에 공유하여 텍스트를 저장하는 서비스”를 과제 기간에 맞는 웹 기반 MVP로 축소하는 과정에서 AI와의 논의가 도움이 되었다.

### 8.3 문서화 지원

요구사항 문서, 설계 문서, 테스트 계획, 품질 관리 문서를 작성할 때 구조를 잡는 데 도움이 되었다.  
이를 통해 개발 과정이 GitHub에 체계적으로 남을 수 있었다.

### 8.4 문제 해결 지원

OCR, DB 저장, 검색 기능 구현 중 막히는 부분에 대해 빠르게 해결 방향을 찾을 수 있었다.

## 9. 바이브코딩의 한계

바이브코딩의 한계도 확인하였다.

### 9.1 코드 품질 검증 필요

AI가 생성한 코드는 빠르게 동작할 수 있지만, 항상 최적의 구조나 충분한 예외 처리를 포함하지는 않았다.

### 9.2 요구사항 해석 오류 가능성

AI가 제안하는 기능이 과제 범위에 비해 너무 크거나, 실제 필요한 기능보다 과도할 수 있었다.  
따라서 개발자가 요구사항 우선순위를 판단해야 했다.

### 9.3 검색 품질 문제

유사도 검색 기능은 구현 자체는 가능했지만, 실제 검색 결과가 기대와 다를 수 있었다.  
이는 AI가 제안한 기술을 적용하더라도 실제 품질 검증이 필요하다는 점을 보여준다.

### 9.4 개발자의 이해 필요

AI가 작성한 코드를 이해하지 않고 사용하면, 오류 발생 시 수정이 어렵다.  
따라서 바이브코딩은 개발자를 대체하는 것이 아니라, 개발자의 판단과 검토를 보조하는 방식으로 활용해야 한다.

---

## 10. 프로세스 적용의 종합 교훈

이번 프로젝트를 통해 얻은 가장 큰 교훈은 다음과 같다.

> 바이브코딩은 개발 속도를 높여주지만, 좋은 소프트웨어를 만들기 위해서는 요구사항 분석, 설계, 테스트, 품질 관리가 반드시 함께 필요하다.

구체적인 교훈은 다음과 같다.

1. 요구사항 분석을 통해 구현 범위를 줄이는 것이 중요하다.
2. 설계 없이 바로 코딩하면 기능이 늘어날수록 구조가 복잡해진다.
3. AI가 만든 코드는 반드시 프로젝트 구조에 맞게 검토해야 한다.
4. 기능이 동작하더라도 실제 품질은 테스트를 통해 확인해야 한다.
5. OCR과 유사도 검색처럼 불확실성이 있는 기능은 사용자 수정과 예외 처리가 필요하다.
6. 품질 문제를 발견하고 개선한 기록은 소프트웨어공학 프로세스의 중요한 증빙이 된다.
7. GitHub 커밋과 날짜별 토의 기록은 지속적인 개발 과정을 보여주는 데 효과적이다.

## 11. 결론

CapBox 프로젝트는 바이브코딩을 활용하여 짧은 기간 안에 OCR 기반 스크린샷 아카이빙 웹앱을 구현한 사례이다.

바이브코딩은 코드 초안 작성, 아이디어 구체화, 문서화에서 효과적이었지만, 구현 결과의 품질을 보장하지는 않았다.  
따라서 요구사항 분석, 설계, 테스트, 품질 관리와 같은 소프트웨어공학 프로세스를 함께 적용해야 했다.

결과적으로 본 프로젝트는 바이브코딩이 단순한 즉흥적 코딩 방식이 아니라, 체계적인 개발 프로세스와 결합될 때 더 효과적으로 활용될 수 있음을 보여준다.ㄴ
